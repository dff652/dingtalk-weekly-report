# 输入、缺失处理与输出契约

## 用户必须提供或确认

| 阶段 | 输入 | 未提供或不合法时 |
|---|---|---|
| 首次配置 | 姓名、表单项目与附件项目，以及本人/管理员确认的 URL、字段 ID、按钮文本、枚举 | `config.json` 校验失败并列出字段；不登录、不填表；不得从公开仓库猜测组织值 |
| 目标周 | 可选的周一日期 | 周一默认上一周；其他日期默认本周；执行前仍由用户确认 |
| 工作内容 | 工作日志文件、含 `docs/report/PROGRESS_REPORT.md` 的项目目录，或逐日口述内容 | 留空时生成 TODO 骨架并进入访谈；路径或标准文档失效时阻断；不得扫描仓库或用 git log 猜测 |
| 登录 | 有效登录态，或用户扫码/在本机终端隐藏输入 auth 链接 | 阻断并要求用户重新登录；Agent 不接收 auth 链接 |
| 人工审核 | 逐日内容、工时合计、同周旧草稿检查 | 不得使用 `--draft --confirmed`；工具没有提交能力 |

`config.json` 的完整字段模板见 `assets/config.example.json`。配置 schema 当前为
`config_version=2`，表单元数据见 `references/FIELDS.md`。`progress_report` 是唯一可选的业务输入；
文件路径直接读取，项目目录只解析固定的 `docs/report/PROGRESS_REPORT.md`。没有工作日志不等于
可以自动编造内容，必须由用户逐日补充。

### 工作日志的格式契约

**工作日志不是本技能生成的，也没有模板**——它是**你自己维护的文件**，本技能只读取它。
`extract_week.py` 靠两个固定标题形态抽取，写不对不会报错，只会得到一整周 TODO 占位：

```markdown
## 3. 每日工作详情

### 7月20日（当天做了什么，这句会成为该日「主要工作内容」初稿）
正文随意，解析只取上面那行括号里的标题。

### 7月18日 ~ 7月19日
区间标题：区间内每天都算「有记录但无独立标题」，仍会置 TODO 要求补写。

## 4. 周报

### Week 30（2026-07-20 ~ 2026-07-24）— 本周主题
```

要点：

- 日期标题必须是 `### N月N日（标题）`，中文「月」「日」，年份由目标周就近推断；
  括号可省略，但省了就没有标题可抽，等同于该日无记录。
- 周条目必须是 `### Week <数字>（YYYY-MM-DD ~ ...）— 标题`，破折号是 `—`。
  只用于生成周总结骨架，正文仍需人工挑选。
- **只有工作日（周一至周五）会被生成为行**；缺任何一个工作日，`validate_report` 会以
  「工作日未覆盖」阻断，附件和填表都进行不下去。
- 抽取产物是**草稿**。日志里没有的日子一律置 TODO，**不会**用 git log、代码或提交记录
  推测补全——那是向 HR 的正式工时申报，把已有证据扩写成未发生的事实不可接受。
  没有日志时改走逐日访谈，由用户口述。

`extract_week.py` **拒绝覆盖已存在的** `weeks/week_report_YYYYMMDD.json`（防止冲掉人工修改）。
补完日志后要重新抽取，先把旧文件改名或删除。

首次配置与后续变更均通过 `scripts/configure.py`：`--show`/`--check` 只读，默认进入交互更新。
新配置必须整体校验通过才原子替换，旧配置保留为 `$WORK/config.json.bak`。一次性 entry/auth
登录链接不是表单地址，配置工具必须拒绝保存。

`$SKILL` 只含 Apache-2.0 通用代码与空白模板；`$WORK` 必须位于技能/源码仓库之外。真实表单 URL、
字段 ID、枚举、项目、周报、截图和登录态都是用户私有运行数据，不属于可提交产物。

## 中间产物与最终输出

| 产物 | 路径/位置 | 用途 |
|---|---|---|
| 周报 JSON | `$WORK/weeks/week_report_YYYYMMDD.json` | 人审锚点；已存在时拒绝覆盖 |
| 附件 | `$WORK/output/YYYYMMDD-YYYYMMDD本周工作总结与下周计划.xlsx` | 上传到周报表单 |
| 填表预览 | `$WORK/output/shots/20-filled-review.png` | 暂存前核对字段、行数、工时 |
| 暂存结果 | `$WORK/output/shots/30-saved.png` + 氚云草稿 | 工具可到达的最终状态 |
| 配置备份 | `$WORK/config.json.bak` | 最近一次重新配置前的配置 |
| 登录态 | `~/.config/dtwr/state.json`，权限 0600 | 凭证，不得入库或转发 |

最终“提交”不属于工具输出：用户必须在钉钉中打开草稿、再次核对并亲手提交。
`--confirmed` 只是操作者已完成人审和旧草稿检查的声明，不提供身份认证、不可抵赖或审计证明。
一次性 auth 链接不得出现在聊天、命令参数、shell 历史、文件或 git；`--login-url`
只接受用户在交互终端中的隐藏输入。

## 失败原则

- 配置占位值、TODO、空必填项、错误 schema、错误周次、工作日缺失、非法枚举、工时异常、
  内容超过 200 字：
  在生成附件或填表前阻断，并一次列出全部问题。
- 每行工时必须 `>0` 且 `≤24`，同日合计不得超过 24h；错误值必须由用户更正，不得猜测、
  拆分到其他日期或静默修正。
- 项目下拉无法精确选中、附件不存在、暂存后未观察到成功提示：
  返回失败并保留 `99-error.png`，不声称成功。
- `form_texts.save_draft` 指向提交按钮时阻断；工具永远不允许把“提交”配置成草稿动作。
- 同周旧草稿目前无法可靠自动识别：由用户检查，`--confirmed` 是显式确认。
- `$WORK`/登录态属主自动检查仅在 POSIX 系统启用；Windows 依赖用户目录 ACL，验收时需人工确认账户隔离。
